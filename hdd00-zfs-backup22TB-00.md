Я изучил твой файл с результатами команд. Теперь можно составить инструкцию не для абстрактного диска, а конкретно для твоего накопителя, пула ZFS и Raspberry Pi.

## 2. План диагностики

Я предлагаю следующий порядок.

Первый запуск и обнаружение ZFS

Уже успешно выполнено

1\. Идентификация HDD и SMART

Наработка, ошибки, температура, состояние электроники

2\. Short и Extended SMART Self-Test

Внутренняя диагностика накопителя

3\. Полное чтение поверхности HDD

Проверка доступности всех 22 TB через USB

4\. Импорт ZFS только для чтения

Проверка состояния пула и поиск архивных манифестов

5\. Контрольные суммы фото и видео

Повторный расчёт, сравнение с оригиналами, отчёт об ошибках

6\. ZFS scrub (отдельный этап)

Проверка всех занятых блоков с контрольными суммами ZFS

7\. Корректный экспорт и отключение

Без обрыва операций и принудительного выключения

Если это единственная копия фотографий и видео, я рекомендую изменить приоритеты: после первичного SMART сначала скопировать невосполнимые данные на другой носитель, а уже затем подвергать старый диск многосуточному чтению. Даже неразрушающая проверка создаёт нагрузку на механический HDD.

Ниже — полная процедура, предполагающая, что SMART не выявит серьёзных проблем и данные не требуют немедленного аварийного восстановления.

## 3. Подключение диска с нуля

Все команды рассчитаны на Raspberry Pi с Raspberry Pi OS и уже работающим ZFS. Устанавливать ZFS заново не нужно.

### Шаг 3.1. Включение

Включи питание OWC, дождись раскрутки диска и подключись к Raspberry Pi через SSH.

Проверь устройства:

```
lsblk -o NAME,PATH,SIZE,MODEL,SERIAL,TRAN,FSTYPE,LABEL,MOUNTPOINTS
```

Ожидаем увидеть:

- `sda` — Toshiba MG10AFA22TE, 20T.
- `sda1` — `zfs_member`, метка `backup22TB`.
- `sda9` — 8M, служебный раздел.
- `nvme0n1` — Samsung 990 PRO, системный SSD Raspberry Pi.

Поскольку имя `/dev/sda` может измениться после переподключения USB-устройства, каждый раз проверяй модель и серийный номер перед командами, обращающимися к физическому диску.

Дополнительно:

```
ls -l /dev/disk/by-id/ | grep 'Y430A0S1FM8J'
```

Если соответствующие ссылки существуют, они помогут идентифицировать HDD независимо от номера `/dev/sdX`.

Проверь размер:

```
sudo blockdev --getsize64 /dev/sda
```

И сообщения ядра:

```
sudo dmesg -T | tail -n 100
```

Ошибки USB, сбросы соединения или ошибки I/O на этом этапе требуют разбирательства до продолжения.

### Шаг 3.2. Проверка импортированных пулов

```
sudo zpool list
```

Если вывод:

```
no pools available
```

это ожидаемо: твой пул был экспортирован.

Теперь обнаружим его:

```
sudo zpool import
```

Должен появиться `backup22TB` с состоянием `ONLINE`.

Пока не импортируй пул. Сначала проведём физическую диагностику, для которой файловая система не нужна.

## 4. Диагностика SMART

### Шаг 4.1. Подготовить каталог для отчётов

Создадим каталог на системном NVMe, чтобы отчёты не записывались на проверяемый HDD:

```
mkdir -p ~/hdd-logs/backup22TB
```

Установим необходимые утилиты, если их ещё нет:

```
sudo apt update
sudo apt install smartmontools tmux
```

Обнаружим SMART-устройства:

```
sudo smartctl --scan-open
```

### Шаг 4.2. Получить полный SMART-отчёт

Сначала:

```
sudo smartctl -x /dev/sda
```

Если OWC не передаёт ATA-команды автоматически, попробуй:

```
sudo smartctl -x -d sat /dev/sda
```

Параметр `-d sat` поддерживает ATA passthrough через совместимый USB-SATA-контроллер.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



Когда команда корректно покажет модель Toshiba и серийный номер `Y430A0S1FM8J`, сохрани исходный отчёт. Ниже я предполагаю, что работает вариант `-d sat`:

```
sudo smartctl -x -d sat /dev/sda \
  | tee ~/hdd-logs/backup22TB/smart-before.txt
```

Если работает только команда без `-d sat`, используй её в дальнейших шагах.

Что нас интересует: `Reallocated_Sector_Ct`, `Current_Pending_Sector`, `Offline_Uncorrectable`, история SMART Self-Test, наработка в часах и температура.

Если обнаружатся ожидающие переназначения сектора или ошибки чтения, не стоит немедленно запускать все стрессовые тесты. Сначала нужно оценить отчёт и наличие резервной копии.

### Шаг 4.3. Короткий SMART Self-Test

```
sudo smartctl -t short -d sat /dev/sda
```

После указанного утилитой времени:

```
sudo smartctl -l selftest -d sat /dev/sda
```

Желаемый результат:

```
Completed without error
```

### Шаг 4.4. Длинный SMART Self-Test

Если короткий тест успешен:

```
sudo smartctl -t long -d sat /dev/sda
```

Этот тест выполняется внутри самого HDD. Команда выведет ожидаемое время окончания.

В ходе теста можно проверять состояние:

```
sudo smartctl -c -d sat /dev/sda
```

После завершения:

```
sudo smartctl -l selftest -d sat /dev/sda
```

Если тест поддерживается и заканчивается `Completed without error`, это важный положительный результат. SMART хранит журнал диагностических тестов, включая ошибки и, при наличии, адрес первого проблемного сектора.&#x20;

Debian Manpages



Во время Long Self-Test я бы не запускал другие интенсивные операции с диском. Дай ему закончить проверку.

## 5. Полное последовательное чтение 22 TB

Это отдельная проверка, и в твоём случае она полезна: мы проверим не только диск, но и стабильность чтения через USB-док OWC в течение длительного времени.

Важно: этот этап выполняем только после успешного SMART и при отсутствии подозрительных симптомов. ZFS-пул должен оставаться экспортированным.

Проверь:

```
sudo zpool list
```

Потом ещё раз подтверди, что `/dev/sda` — Toshiba, а не другое устройство.

### Запуск в tmux

```
tmux new -s hdd-surface-test
```

В открытой сессии:

```
sudo dd \
  if=/dev/sda \
  of=/dev/null \
  bs=16M \
  iflag=direct \
  status=progress
```

Это операция чтения, не записи. `dd` будет читать все доступные блоки диска и отбрасывать данные.

После завершения обязательно проверь код возврата:

```
echo "dd exit code: $?"
```

`0` означает, что чтение завершилось без ошибки, о которой сообщил `dd`.

Не добавляй `conv=noerror`: сейчас нам важно обнаружить первую ошибку и разобраться, а не пропустить её.

Чтобы отсоединиться от tmux и оставить процесс работающим, нажми `Ctrl+B`, затем `D`.

Вернуться в сессию:

```
tmux attach -t hdd-surface-test
```

На 22-ТБ HDD эта операция может занять несколько суток, в зависимости от скорости чтения и контроллера USB.

Я бы выделил на неё отдельный период, без одновременного SMART Long Self-Test, scrub или расчёта хешей. Команда проверяет доступность блоков, но не проверяет контрольные суммы ZFS или содержимое фотографий.

### Что проверить после окончания

Ещё раз сохрани SMART:

```
sudo smartctl -x -d sat /dev/sda \
  | tee ~/hdd-logs/backup22TB/smart-after.txt
```

И сравни начальные и конечные отчёты:

```
diff -u \
  ~/hdd-logs/backup22TB/smart-before.txt \
  ~/hdd-logs/backup22TB/smart-after.txt
```

Различия во времени работы, температуре и счётчиках активности ожидаемы. А вот появление переназначенных секторов, ожидающих секторов или новых неисправимых ошибок уже требует анализа.

Проверь системный журнал на наличие ошибок:

```
sudo journalctl -k --since today \
  | grep -Ei 'sda|I/O error|medium error|uas|usb.*reset'
```

Отдельные информационные сообщения `uas` или `sda` не означают неисправность. Ищем именно ошибки передачи, чтения и сбросы устройства.

Если все тесты прошли успешно, можно переходить к файловой системе.

## 6. Безопасный импорт ZFS только для чтения

Эти команды уже проверены на твоём оборудовании — именно с ними ты успешно открывал архив.

Создадим точку монтирования:

```
sudo mkdir -p /mnt/zfs-inspect
```

Убедимся, что пул экспортирован:

```
sudo zpool list
```

После этого импортируем:

```
sudo zpool import \
  -N \
  -o readonly=on \
  -R /mnt/zfs-inspect \
  backup22TB
```

Три параметра обеспечивают безопасный режим:

- `-N` — не монтировать datasets сразу.
- `-o readonly=on` — импортировать пул только для чтения.
- `-R /mnt/zfs-inspect` — временно перенаправить точки монтирования и не сохранять этот импорт в `zpool.cache`.

Это соответствует официальной процедуре OpenZFS для осторожного импорта.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://openzfs.github.io\&sz=32)

OpenZFS documentation



Проверим, что пул действительно read-only:

```
sudo zpool get readonly,altroot backup22TB
```

Ожидаемые значения:

```
readonly  on
altroot   /mnt/zfs-inspect
```

Затем:

```
sudo zpool status -v backup22TB
```

И информация о datasets:

```
sudo zfs list -r backup22TB
```

### Подключаем файловые системы

Поскольку у тебя в этой ситуации импортирован только один пул:

```
sudo zfs mount -a
```

Проверяем:

```
sudo zfs mount
```

В твоём случае уже подтверждены следующие пути:

```
/mnt/zfs-inspect/backup22TB
/mnt/zfs-inspect/backup22TB/media
```

Теперь архив доступен:

```
ls -lah /mnt/zfs-inspect/backup22TB/media
```

И каталоги по годам:

```
ls -lah /mnt/zfs-inspect/backup22TB/media/2024
```

```
ls -lah /mnt/zfs-inspect/backup22TB/media/2025
```

Все операции сейчас выполняются в режиме, запрещающем запись на ZFS-пул.

## 7. Поиск исходных контрольных сумм фотографий и видео

Это один из наиболее важных этапов для твоего архива.

ZFS проверяет внутреннюю целостность блоков, но нам нужно дополнительно убедиться, что файлы остались побайтово идентичными оригиналам, с которых когда-то были рассчитаны контрольные суммы.

Для этого нам понадобятся сохранённые файлы-манифесты: SHA-256, SHA-512, MD5 или другого формата.

### Шаг 7.1. Найти файлы с контрольными суммами

Выполни:

```
sudo find /mnt/zfs-inspect/backup22TB \
  -type f \( \
    -iname '*checksum*' -o \
    -iname '*sha256*' -o \
    -iname '*sha512*' -o \
    -iname '*md5*' -o \
    -iname '*hash*' -o \
    -iname '*manifest*' -o \
    -iname '*.sfv' -o \
    -iname '*.b3' \
  \) -print
```

Команда ничего не меняет и рекурсивно ищет файлы, названия которых похожи на манифесты контрольных сумм.

Если она ничего не найдёт, проверим также текстовые файлы:

```
sudo find /mnt/zfs-inspect/backup22TB \
  -type f -iname '*.txt' -print
```

Важный момент: я пока не знаю, в каком формате ты сохранял контрольные суммы в 2024–2025 годах. Поэтому не стану предполагать, что это именно SHA-256.

### Шаг 7.2. Определить формат

Когда найдём манифест, посмотрим первые строки, например:

```
sed -n '1,10p' "/путь/к/файлу/SHA256SUMS"
```

В стандартном формате SHA-256 содержимое выглядит примерно так:

```
a81c...  2024/IMG_0001.HEIC
c42f...  2024/IMG_0002.MOV
d813...  2025/VID_0001.MP4
```

В реальном файле вместо сокращённых значений будут полные хеши.

Имя файла, указанное после контрольной суммы, очень важно: от него зависит, из какого рабочего каталога запускать проверку.

Например, если в манифесте указано `2024/IMG_0001.HEIC`, а сам архив расположен в `media`, проверку нужно запускать из `media`.

## 8. Пересчёт и сравнение контрольных сумм

Предположим, после осмотра выяснилось, что у тебя SHA-256-манифест `SHA256SUMS`, находящийся в корне `media`, и пути внутри него относительны к этой директории.

Тогда выполняем:

```
cd /mnt/zfs-inspect/backup22TB/media
```

Проверка:

```
sha256sum --check --strict --quiet SHA256SUMS \
  > "$HOME/hdd-logs/backup22TB/checksum-verify.log" 2>&1
```

Затем сразу после завершения:

```
echo "Exit code: $?"
```

Посмотреть ошибки:

```
cat ~/hdd-logs/backup22TB/checksum-verify.log
```

Обрати внимание: это пример для конкретного стандартного формата. Прежде чем выполнять, нужно проверить настоящий манифест и указанные в нём пути.

`sha256sum --check` самостоятельно перечитывает каждый перечисленный файл, вычисляет SHA-256 и сравнивает его с сохранённым значением.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://www.gnu.org\&sz=32)

GNU



### Как интерпретировать результат

| Результат                              | Значение                                         |
| -------------------------------------- | ------------------------------------------------ |
| Exit code `0`                          | Все перечисленные контрольные суммы совпали      |
| `FAILED`                               | Содержимое файла отличается от сохранённого хеша |
| `No such file`                         | Файл отсутствует по ожидаемому пути              |
| `Permission denied`                    | Недостаточно прав для чтения                     |
| `no properly formatted checksum lines` | Неверный формат манифеста или выбранная утилита  |

Не используй `--ignore-missing`: он позволит пропустить отсутствующие файлы, а нам необходимо обнаружить и их.

Также нельзя считать несовпадение хеша автоматическим доказательством физической неисправности HDD. Файл мог измениться после создания манифеста, например при изменении EXIF-метаданных фотографии.

### Если контрольные суммы были MD5 или SHA-512

Команды отличаются только алгоритмом:

```
md5sum --check --strict --quiet MD5SUMS
```

или:

```
sha512sum --check --strict --quiet SHA512SUMS
```

Для обнаружения случайных повреждений MD5 также может быть полезен, хотя для новых манифестов я рекомендую SHA-256. MD5 не следует использовать как криптографическое доказательство подлинности файлов.&#x20;

### Важное ограничение проверки

Даже если `sha256sum -c` сообщает об успешном результате, он подтверждает только файлы, которые перечислены в манифесте.

Чтобы удостовериться в полноте архива, отдельно понадобится:

1. Сравнить перечень файлов в манифесте с реальным содержимым каталога.
2. Найти файлы, отсутствующие в архиве.
3. Найти файлы, существующие в архиве, но не перечисленные в манифесте.
4. Сверить количество файлов по годам и общий объём данных.

Последний пункт особенно важен: 100% совпадений контрольных сумм не доказывают, что в манифесте перечислено 100% исходного архива.

Я предлагаю выполнить эту дополнительную проверку после того, как мы увидим формат твоих файлов контрольных сумм.

## 9. Создание нового манифеста на 2026 год

Если старые контрольные суммы совпали и все необходимые файлы обнаружены, полезно создать новый независимый манифест.

Например, для всех файлов в `media`:

```
cd /mnt/zfs-inspect/backup22TB/media
```

```
set -o pipefail

find . -type f -print0 \
  | sort -z \
  | xargs -0 -r sha256sum \
  > "$HOME/hdd-logs/backup22TB/sha256-2026.txt"
```

После выполнения:

```
echo "Exit code: $?"
```

Полученный файл будет находиться на NVMe Raspberry Pi, а не на проверяемом HDD.

Этот способ корректно обрабатывает обычные и нестандартные имена файлов, в том числе с пробелами. Утилиты GNU умеют экранировать специальные символы имён при формировании контрольных сумм.

Сохрани копию полученного манифеста также вне Raspberry Pi, например на другом накопителе. Если хеши и архив находятся только на одном физическом диске, это не независимая резервная копия.

## 10. Проверка целостности ZFS: scrub

Здесь есть принципиальное отличие от обычного чтения файлов.

`zpool scrub` перечитывает выделенные ZFS блоки и проверяет контрольные суммы, записанные в метаданных ZFS. Это позволяет находить скрытые повреждения данных.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://openzfs.github.io\&sz=32)

OpenZFS documentation



Но scrub нельзя запускать на пуле, импортированном через `readonly=on`.

Это не просто ограничение функциональности: в некоторых версиях OpenZFS попытка запустить scrub на read-only-пуле приводила к зависанию команды. Исправление такого поведения включено в OpenZFS 2.4.0.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

GitHub



Поэтому scrub — отдельный этап, который мы будем выполнять после остальных проверок и при наличии резервной копии важных данных.

### Шаг 10.1. Экспортировать read-only-пул

Сначала выйти из каталогов архива:

```
cd ~
```

И экспортировать:

```
sudo zpool export backup22TB
```

### Шаг 10.2. Импортировать пул для чтения и записи

```
sudo zpool import \
  -N \
  -R /mnt/zfs-inspect \
  backup22TB
```

Обрати внимание: здесь нет `-o readonly=on`.

Проверим:

```
sudo zpool get readonly backup22TB
```

Должно быть `off`.

Файловые системы монтировать необязательно — scrub работает на уровне пула.

### Шаг 10.3. Запустить scrub

```
sudo zpool scrub backup22TB
```

Следить за состоянием:

```
sudo zpool status -v backup22TB
```

Проверка завершится, когда появится сообщение о законченном scrub, а не `scrub in progress`.

Желаемый результат:

```
scan: scrub repaired 0B ... with 0 errors
```

В случае обнаружения повреждений ZFS может определить проблемные блоки, но у твоего одиночного HDD нет второго независимого диска для восстановления повреждённых данных.

После завершения:

```
sudo zpool export backup22TB
```

Итак, эту проверку мы специально оставляем на конец, потому что она требует импорта пула с возможностью записи.

## 11. Правильное отключение диска и Raspberry Pi

Это постоянная процедура, которую можно применять после любых проверок.

Остановить все операции

Дождаться завершения SMART Self-Test, dd, вычисления хешей или scrub.

Выйти из каталога ZFS

```
cd ~
sync
```

Экспортировать пул

```
sudo zpool export backup22TB
```

Если пул уже экспортирован, повторно делать это не требуется.
